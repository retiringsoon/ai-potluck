# potluck — 和你信得过的人拼 AI 额度

> **状态：招募早期用户。** 这既是一份方案说明，也是一份求助信：看完思路、上手试一试，然后
> 告诉我们什么才能让它对你真正有用（见[我们在问什么](#我们在问早期用户)）。英文版：[PROPOSAL.md](PROPOSAL.md)。
>
> **TL;DR（可直接复制到群里）**：我们做了一个开源小工具，让社区成员安全地拼着用 AI 额度——
> 有额度的人在自己电脑上跑一个小 connector 共享出去（API key 永远不出本机），其他人拿邀请码
> 加入，一条命令提问、按用量记账，每一笔都有双方签名和可离线验证的收据。想找第一批用户帮忙
> 试装、试用、提需求（仓库地址随发布帖附上）。

## 问题

AI 模型的访问是不均的：有人有花不完的企业 API 额度，有人显卡上跑着
vLLM，有人只是偶尔想要一个好模型、却不想开五个号。拼单本身没问题——**问题出在钥匙和钱**：

- 把 API key 手抄来手抄去，等于埋了一颗安全事故的雷；
- "回头转你"撑不过三个人，没人信任一张共享表格；
- 出了问题（数字不对、节点抽风、账单有争议）时，没有一份大家公认的账可查。

现有网关解决的是"聚合"（一个 key 前面挂一堆模型），不解决"多方之间的信任"——因为它们假设
运营者是一个人。

## 思路

**potluck 是小型 AI 共享圈的信任层。** 圈子里跑一个轻量中心，成员各选一边：

- **贡献者**在自己电脑上跑 connector，共享一个上游（API 端点或自部署模型）。
  **上游凭据永远不出本机**——存在 0600 权限的本地文件里，不上传、不打印、不经手中心。
- **消费者**拿邀请码加入，`potluck ask "..."` 拿到流式回答和一行费用（带收据号）。

每份用量由**执行方设备签名**；每笔结算由**中心签名**并锚进一条只增不改的 **Merkle 透明日志**。
任何人拿到收据都能离线核验五件事：签名、计量来源、分账数学、账本包含性、账户史完整。两侧账目
用 `share reconcile` / `admin reconcile` 对账，对不上会指名道姓说是哪一条。

## 一次请求的实际旅程

三个程序，三种网络角色。**只有中心监听端口**；节点和消费者都是出站连接——家庭 NAT 和防火墙
不受影响，任何一方都不需要端口转发。

```text
                   ┌───────────────────────────┐
                   │  中心 —— 一台小机器         │
                   │  身份注册表、邀请码          │
                   │  credit 账本 + 预占         │
                   │  派单、内容中继             │
                   │  结算、收据、透明日志        │
                   └──────▲─────────────▲──────┘
         出站 WSS         │             │   HTTPS + SSE
         （节点主动拨出，  │             │   （带签名的请求）
          无入站端口）     │             │
         ┌────────────────┴───┐   ┌─────┴────────┐
         │ 贡献者机器           │   │ 消费者        │
         │ · 保管上游 API key   │   │ · 每笔请求    │
         │   （0600，仅本机）    │   │   先签名      │
         │ · 直接调用上游        │   └──────────────┘
         └─────────┬───────────┘
                   │ TLS
         ┌─────────▼───────────┐
         │ 上游（API 或         │
         │ 自部署模型）          │
         └─────────────────────┘
```

一次 `ask` 从头到尾：

1. **签名。** 你的 CLI 组装请求（prompt、模型、消费上限、有效期），用你的 Ed25519 密钥签一份
   消费授权：写明**这一笔**请求、**你的**账户、你接受的最大扣费。签名放在请求头里，私钥从不
   离开本机。
2. **预占。** 中心验签、查余额，然后**预占**这笔上限——同一笔钱不可能被扣两次。
3. **派单。** 中心挑一个在线且服务该模型的节点，把 offer 推进节点早已建立好的出站链路。节点
   拿本地限额核一遍条款——可以拒绝，中心也抬不高它的限额。
4. **执行。** 节点**在自己机器上、用自己的 key** 直接调用上游。模型还在写的时候，文本增量就
   经中心中继到了你的终端。
5. **上报与结算。** 节点对用量报告做设备签名；中心验双方签名与上限，按固定权重分账：你的
   预占 → 贡献者账户。你拿到收据号，收据锚进透明日志。
6. **出问题的时候。** 没有节点在线 → 几秒内告诉你，且不创建请求；节点干活干到一半挂了 →
   换节点重试或带原因失败；用量无法确定的记为**待核对**，绝不静默按零计费；Ctrl-C →
   真正的端到端取消，会传到在途的 attempt。

### 中心做什么——以及不能做什么

| 中心…… | |
|---|---|
| **保管** | 身份与密钥注册表、邀请码、credit 账本与预占、透明日志 |
| **执行** | 验签、派单、中继流式增量、结算、签发收据、提供审计端点 |
| **绝不保管** | 上游 API key——它们只存在于贡献者机器上 |
| **绝不做** | 自己调用上游；没有你的逐笔签名就动你的余额；抬高节点的本机限额 |

中心是**可追责**的一方，不是无所不能的一方。它伪造不了贡献者的用量报告（设备签名），没有
你的逐笔签名也动不了你的余额——但账本确实由它记账，结算密钥也在它手里。正因如此，每笔结算
都签名并锚进只增不改的透明日志，且审计命令（`verify receipt`、`share reconcile`
、`admin reconcile`）全部可离线核验：**对不上账的记账，会被指名道姓地发现**。

### 谁能看到什么

| 参与方 | 能看到你的 prompt？ | 能看到上游 key？ | 能动你的 credit？ |
|---|---|---|---|
| 中心运营者 | 能——中继并存储请求 | 不能 | 仅限你签名过的单笔上限内 |
| 贡献者节点 | 能——它要执行模型 | 只有自己的 | 只能按结算收据赚取 |
| 上游服务商 | prompt 本身（它提供服务） | —— | 不能 |

**保留策略默认（拟定）**：中心永久保留的只有账务数据——用量、金额、模型、签名——外加内容
哈希。prompt 只存哈希，已交付的输出在争议窗口后清除；想把内容留作训练数据必须是双方显式
opt-in（贡献者披露 + 消费者同意），绝不默认开启。收据与对账在任何模式下都基于哈希。

**网络实操**：中心只需要被所有成员可达——一台小型公网 VPS、一个 Tailscale 网络、或局域网
都可以。节点和消费者只发出站连接。中心开 TLS（自带证书或反代终结）时，prompt 的每一跳都是
加密的：消费者 → 中心 → 节点 → 上游。线协议细节见 [README](../README.md#文档) 链接的网络契约。

## 现在能用到什么（v0.1.0）

这是一个能跑的系统，不是白皮书：

- **邀请制上手**——运营者签发邀请码（带角色、额度、有效期、使用次数）。消费者和贡献者各一条
  命令加入；密钥本机生成、身份由服务端派生；不改 JSON、不拷 token；重复加入幂等。
- **`ask`**——流式（`--stream`）或整段回答；模型自动从在线节点推断；失败会告诉你原因和下一步
  （比如"没有节点能接：预算 20000 > 节点本机敞口 5000"）；Ctrl-C 是真正的端到端取消。
- **贡献**——`share setup` 向导配置上游地址/Key/模型，自检只探测连通性、绝不发送你的 Key；
  `share run/pause/resume/status` 管理共享状态；保守的本机限额（并发、在途敞口）本地强制，
  中心抬不高。
- **收据与审计**——`potluck verify receipt` 五维离线核验；`share reconcile` /
  `admin reconcile` 双边对账，有差异会指名是哪条记录。三个命令全部只读，且拒绝打开不存在的
  数据库（不静默建库）。
- **中心**——单进程 + 内嵌 SQLite（不需要装数据库），一个端口承载 HTTP/WebSocket/SSE，进程
  自带 TLS 或交给反代；部署文档含 systemd/launchd/备份手册；重启从磁盘恢复，崩溃窗口有测试。
- **发布质量**——每个发布包过自动门禁：干净工作树 → 干净 venv 离线装 wheel → 真实进程端到端
  冒烟，全过才打包；包内 `RELEASE_INFO` 钉死对应 commit。

以上全部有约 1900 个测试、`ruff`、`mypy --strict`（零告警）守着。

## 设计原则

1. **凭据永远不离开挣到它的那台机器。** 中心只派活，绝不保管上游 key。
2. **签名证明"谁报的"，不证明"是真的"。** 每个用量数字都带证据等级。今天一切都是
   `node_reported`（贡献者自报）；收据让上报**可归责、可审计**，但不假装它无所不能。更高等级
   （平台可见流量、可信硬件计量）是路线图决策，不是营销话术。
3. **本机限额是最终限额。** 中心抬不高贡献者的并发与敞口；节点拒绝运营者没点头的工作。
4. **刻意做小。** 一个 Python 进程、内嵌 SQLite、一个端口。社区中心应该能部署在一台 5 美元的
   VPS 上、一个下午看懂。
5. **邀请制优先。** 这是给彼此认识的圈子做的；陌生人规模的经济学（和攻击面）在信任机制攒够
   之前明确不做。
6. **失败要响。** 缺数据是带下一步指引的错误，绝不是静默的成功。

## 这不是什么

- **不是陌生人市场。** 没有公开挂单，没有开放注册。
- **不是代币经济。** credit 是内部记账单位；没有币、没有炒作、不托管真钱。
- **不匿名。** 贡献者的机器执行你的 prompt，也读得到它。文档里我们直说：跟你信的人用。
- **不是绕过上游条款的工具。** 只支持 L1 供给：自己的 API key、自部署模型、有权共享的额度。
  共享个人包月订阅通常违反上游服务条款——我们不支持，也不会为它做功能。

### 下一步：让任何工具直接用（OpenAI 兼容 API）

`ask` 验证了整条管道；真干活时你不该被迫离开自己的工具。下一里程碑把池子暴露成一个
**OpenAI 兼容端点**：

```text
base_url = https://<你的中心>/v1
api_key  = <potluck 签发的 API key>
model    = <你圈子里节点在服务的模型>
```

- 中心签发**可撤销、绑定你账户、带 credit 上限的 API key**。每个工具请求在该上限内自动授权
  ——预占、结算、签名收据、透明日志全部与今天相同，审计故事一点不变。
- agent 循环（工具调用、多轮）原生可用：每一轮就是一次请求，上下文由你的 agent 自己管理，
  按 key/按请求的成本依旧可对账。
- 诚实的权衡：用中心签发的 key 时，由中心在你设的上限内自动代签逐笔授权——你给了它一笔
  有界的、随时可撤销的花钱权限。希望签名留在自己机器上的用户（设计原则 #1，与贡献者
  connector 对称），规划中有一个**本地签名代理**配套。
- 这同时解锁长程 agent 任务：agent 循环对接端点后，除 base_url 和 key 外零 potluck 专属配置。

## 我们在问早期用户

任选几条回答，开 issue 或讨论都行，一句话也欢迎：

1. **供给侧**：你想共享什么——OpenAI 兼容 API、Anthropic、本地 `ollama` / `vLLM`，还是别的？
   什么样的端点形态是我们必须支持的？
2. **消费侧**：API 接入已是**确认的下一里程碑**（见上方“下一步”）——告诉我们你会把哪些
   工具指过来（IDE 插件、agent 框架、脚本、聊天界面），以及它们需要什么（流式、工具调用、
   模型列表、prompt 缓存头）。
3. **经济模型**：你的圈子里 credit 应该怎么玩？管理员统一充？贡献者赚了再花？按模型定价？
   每人每天限上限？
4. **平台**：你的社区实际用什么（macOS / Linux / Windows / Docker）？中心的 Docker 镜像
   是不是必需品？
5. **信任**："贡献者能读到 prompt"在你的圈子里能接受吗？什么缓解措施会改变答案（prompt
   脱敏、可选的纯本地模式、证据升级）？
6. **就一件事**：缺了哪一个能力，你会每周都用它？

## 怎么参与

- **安装**：拿发布包，解开跑 `./install.sh`（macOS/Linux，Python 3.11+；离线可装，包内自带
  依赖 wheel）。然后照 [README](../README.md)：一条命令加入、一条命令提问、一条命令共享。

  [缺陷模板](../../issues/new?template=bug_report.md) 开 issue（`potluck doctor` 生成脱敏诊断
  可直接附上）。中文一律欢迎。
- **看细节**：网络契约、传输层 ADR、协议背景、以及一份不藏短处的工程评审，都在
  [README 文档区](../README.md#文档)。
